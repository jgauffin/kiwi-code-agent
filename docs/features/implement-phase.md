# Implement phase

A session mode that carries out an approved spec task by task, and is finished when every task is tested and the test commands pass.

- Starts by itself when the docs listing that follows Approve ends: approving is the go-ahead for the build, so it takes no second click. The plan bar's Implement is the way back in when nothing is building the tasks, and refuses a draft or a spec without a tasks file. It continues the mapping run's conversation where the engine resumes, a fresh session otherwise; a feature that already has an implement session carries that session on. It gets no tab of its own: the feature has one tab, and the implementer is a section of its chat, open while it holds the floor.
- Full tool set (Read, Write, Edit, Glob, Grep, JsonSchema, JsonQuery, Bash). Allow writes starts checked: approving the spec is the consent for the writes its tasks map out. Bash and the other tools still prompt, and deny rules still block. A script in the root `package.json` and a command `kiwiAgent.verify` names are exceptions: the user defined them, so they run unprompted unless a deny rule covers them.
- Reads `plan/<feature>.decisions.md` for the rulings: a decision ruled `keep` means the rule stands and the code changes, done with the task that touches it.
- Task state is the tasks file: `[in progress]`, `[done]`, `[tested]`, `[blocked: reason]` appended to the task's line, so task 4 of 7 survives a fresh session. A `proves:` line names, per delivered rule, the test file and the test whose name states the rule.
- Only `[tested]` is a finish. The board goes to verification once every task is tested; the plan bar then stops offering Implement. A blocked task is unfinished work and takes a fresh session.
- The implementer proves its own tasks as it goes, narrowly: `[done]` needs the project holding the code to build, `[tested]` needs the tests on the `proves:` line to pass in a run narrowed to them. Narrow means the nearest project, never the repository, and the `kiwiAgent.verify` commands are named in the prompt so the narrowed run is the same command the sweep will run.
- Verification is the sweep that follows, and answers only what the implementer cannot: whether the feature broke something else. The test commands from `kiwiAgent.verify` run over the files the tasks name when an implement turn ends with the board all tested and no passing run recorded since. A failure goes back to the implement session with the command and its output, and asks for a narrowed reproduction before the sweep is paid for again, up to `kiwiAgent.verifyFailureBudget` consecutive failures; Verify again is offered from the plan bar.
- The implementer follows the task's `how:` block and departs from it only where the code says it cannot be done that way, noting why under the task.
- The plan view's Tasks tab shows, under each scenario, what the task does in the mapper's sentence, its state, the paths it changes and the ones it reads, and its `how:` folded away. The Spec tab shows which task delivers a rule and which test proves it, or `no task` / `no test`. The stepper stands on Implement with the scenario in progress and `x of y tested` beside it, then on Verify.

Not included: claims across sessions, checkpoints, ADO task updates, per-file-type rules injected at edit time.
